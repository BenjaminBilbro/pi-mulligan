## 1. The five NEW bugs — root causes (all validated against source)

### BUG-001 [major] — `to_previous_prompt:true` last_turn silently no-ops (2+ users)

**Root cause (validated):** `protectedOk()` (transforms.ts) computes `protectLatestUser` from
`config.rewind.protectedRoles` (default includes `latest:user`) and returns `false` whenever the
removal set contains `iLatestUser` — with **no awareness of the marker's `to_previous_prompt`
option** (it only receives `(messages, remove, config)`). `resolveLastTurn` CORRECTLY computes the
nuclear removal set including `iLastUser` for the 2+-user case (transforms.test.ts:566 proves
`remove === [3,4,5]`), and CORRECTLY refuses (returns `{remove:[]}`) for the 1-user case
(iFirstUser===iLastUser). But that removal set is then handed to `protectedOk`, which blocks it, and
`filterPipeline`'s `if (!protectedOk(...)) { ... else continue }` silently skips the rewind for the
non-checkpoint granularities. Net: resolver is right, filter undoes it.

**Tool-side gap:** `rewind.ts` step 5b only refuses when `granularity==='last_turn' &&
to_previous_prompt===true && k===0` — i.e. ONLY the 1-user case. The 2+-user case (k>0) is never
caught, so the tool reports success with `k = remove.length` while the filter hides nothing.

**Spec:** PRD §8 explicitly allows the latest user to be removed "unless to_previous_prompt
explicitly and it isn't the first." So nuclear 2+-user MUST work. Success criterion #1 (autonomous
shedding) + design principle #6 (honest bookkeeping) are violated.

### BUG-002 [major] — checkpoint crossing the latest user: partial-apply (trim) instead of refuse

**Root cause (validated):** `filterPipeline`'s `if (!protectedOk(m, remove, config))` block has a
**checkpoint-specific branch** that TRIMS the removal set:
```ts
if (granularity === "checkpoint") {
  let iLatestUser = ...; // last user in m
  remove = remove.filter((r) => r < iLatestUser); // TRIM, not skip
  if (remove.length === 0) continue;
} else { continue; }
```
So a checkpoint rewind whose target precedes the latest user HIDES the messages between the
checkpoint and the latest user, but KEEPS the latest user + current turn → a **non-contiguous view**
[checkpoint-area … latest-user … current-turn] with the middle removed. The tool's `resolvePreview`
computes `k = remove.length` (the FULL pre-trim count) and reports "K messages hidden" while the
filter hides fewer. **Tool/filter K mismatch.**

**Spec:** PRD §6 step 6 ("Refuse if iTarget falls at/before a protected message") + §8 ("a rewind
that removes the latest user … is refused"). The implementation neither refuses (tool) nor no-ops
(filter); it partially applies — contradicting both.

### BUG-003 [minor] — live `last_tool_call_group` fallback inverts under sequential rewinds

**Root cause (validated):** `resolveLastToolCallGroup(units, messages, excludeToolCallId?)` excludes
ONLY the current marker's own `excludeToolCallId`. `filterPipeline`'s live fallback (the `else if
(granularity === 'last_tool_call_group')` branch, taken when `hideEntryIds` is absent/empty) calls it
with the single current marker's id. With two stacked rewinds applied oldest-first: rewind#1 resolves
"last group excluding rewind#1's own call" → finds rewind#2's group → removes rewind#2's confirmation;
then rewind#2 removes rewind#1's confirmation. Net: both mistake spans VISIBLE, both confirmations
HIDDEN — the inverse of intent (spec §11 composition example).

**Mitigation already present:** the `hideEntryIds` PIN arm resolves from pinned entry ids (stable),
so the normal end-to-end flow (agent calls the tool → `resolvePreview` captures `hideEntryIds`) is
CORRECT (pipeline.test.ts:695 PIN test proves both mistakes stay hidden). The live fallback is only
reached when (a) `resolvePreview` threw (no per-entry try/catch — a malformed branch entry makes
`sessionEntryToContextMessages` throw), (b) legacy/externally-created markers, or (c) the pin resolves
empty (compaction). In those cases the inversion happens silently.

**pipeline.test.ts:~720 (LIVE-fallback test)** currently ASSERTS the buggy behavior as documentation:
`expect(JSON.stringify(out).includes("BIG-READ-OUTPUT")).toBe(true)` with the comment "This is NOT a
bug in the live path; it documents WHY hideEntryIds exists." **Fixing BUG-003 flips this assertion to
`false`** — the test must be rewritten to assert the corrected behavior (both mistakes hidden, both
confirmations visible).

### BUG-004 [minor] — `by_content_includes` multi-shrink violates E17 "last wins"

**Root cause (validated):** `applyShrink` calls `resolveShrinkTarget(messages, target)` against the
CURRENT (possibly already-shrunk) message list, and `filterPipeline` applies shrinks oldest-first.
For stable matchers (`by_tool_call_id`, `by_tool_name`) the first shrink's content substitution
preserves `toolCallId`/`toolName` (via `{...orig, content}` spread) → re-resolution finds the same
index → last-wins holds. But `by_content_includes` matches on CONTENT; the first shrink REPLACES the
content, so if the replacement no longer contains the second shrink's needle, `resolveShrinkTarget`
returns `null` on the already-shrunk message → second shrink silently no-ops → FIRST shrink's
replacement persists. E17 ("last wins") is violated.

**Key invariant for the fix:** shrinks never REMOVE messages and never change `role`/`toolCallId`/
`toolName` (spread preserves them). So `by_tool_call_id` and `by_tool_name` are INVARIANT under
shrink; only `by_content_includes` is sensitive to the working-list state. Therefore resolving ALL
shrink targets against the ORIGINAL pre-shrink message list (once, into a stable index map) and then
applying substitutions by index is SAFE for all three matchers and fixes `by_content_includes`.

### BUG-005 [cosmetic] — bloat threshold operator mismatch (`>=` vs `>`)

**Root cause (validated):**
- `nudges.ts` `bloatReminderHandler`: `if (bytes < config.nudges.bloatThresholdBytes) return;`
  → fires when `bytes >= threshold` (INCLUSIVE).
- `audit.ts` `renderAuditReport` rows: `bloaty: messageBytes(msg) > threshold` (STRICT/exclusive).

At exactly the threshold (8192 bytes) the bloat reminder fires but the audit row is NOT flagged ⚠.
`audit.test.ts:295` ("exactly at threshold → NOT flagged (strictly >)") ASSERTS the current
`bloaty=false`. **Fixing BUG-005 flips it to `bloaty=true`** — that test must be updated, and a
matched boundary test added to `nudges.test.ts` to lock the shared semantics.

**Direction chosen:** align audit to `>=` (inclusive) to match the nudge, since the nudge is the
user-facing bloat trigger and `>=` is the safer/more-inclusive choice (an agent following a bloat
reminder with `mulligan_audit` should see the flagged row).

## 2. Shared code-surface coupling (drives the decomposition)

`protectedOk` + `filterPipeline` (the `if (!protectedOk(...))` block) + `rewind.ts` step 5b form a
single correctness surface touched by **BUG-001 AND BUG-002 together**. They must be sequenced
(BUG-001 first per the PRD recommendation; it changes the `protectedOk` signature, which BUG-002's
tool-side guard then reuses). BUG-003/004 also live in `filterPipeline` but in disjoint branches
(the `last_tool_call_group` resolver call and the shrink loop respectively) → independent but same
file → merge-ordered after 001/002. BUG-005 touches only `audit.ts`/`nudges.ts` → fully independent.

## 3. The unified fix architecture (honest bookkeeping)

The cleanest end state makes **the tool the single source of truth for "what K will actually be
hidden"** and the filter a faithful executor:

1. **`protectedOk` gains a `to_previous_prompt?: boolean` param** (BUG-001). When true, the
   `protectLatestUser` block is skipped (the marker explicitly asked to shed the latest user; the
   resolver already refused the 1-user/first-user case). `protectFirstUser` is UNAFFECTED (nuclear
   never touches the first user — the resolver guarantees it). filterPipeline reads
   `rw.options?.to_previous_prompt === true` and passes it through.

2. **The checkpoint-trim branch is REMOVED from `filterPipeline`** (BUG-002 filter side). A
   checkpoint rewind whose removal crosses the latest user now `continue`s (no-op) like every other
   granularity — the filter NEVER partially applies, NEVER produces a non-contiguous view.

3. **`rewind.ts` gains a pre-persist honest-K guard** (BUG-002 tool side, and the missing 2+-user
   half of BUG-001). After `resolvePreview` computes `remove`, run the SAME `protectedOk` check the
   filter will run (with the marker's `to_previous_prompt`); if it would fail, REFUSE before
   persisting (mirror the existing step-5b refusal text family). This guarantees `reported K ===
   actual hidden count` for EVERY granularity — closing the tool/filter mismatch for checkpoint AND
   making the 2+-user nuclear case honest (it now SUCCEEDS and the filter honors it, because step 1
   fixed protectedOk).

4. **`resolveLastToolCallGroup` takes the SET of all rewind `excludeToolCallId`s** (BUG-003).
   `filterPipeline` pre-collects `rewinds.map(rw => rw.excludeToolCallId)` (non-empty strings) into a
   `Set` once before the rewind loop and passes it to the live fallback, so a later rewind can never
   re-target an earlier rewind's own group. Signature: add a 4th param `excludeToolCallIds?: Set<string>`
   (keep the singular one for `resolvePreview`'s single-call usage + backward compat).

5. **`filterPipeline`'s shrink loop resolves ALL targets against the ORIGINAL messages** (BUG-004)
   into a `seq → index` map BEFORE applying any substitution, then applies substitutions by index in
   seq order (last-wins naturally for same-index; different indices all apply). Safe for all three
   matchers (see BUG-004 invariant note).

6. **Align `audit.ts` `bloaty` to `>= threshold`** (BUG-005) to match `nudges.ts`.

## 5. Test gaps the fixes must close (content/identity assertions, not just roles)

Per the PRD's closing recommendation, every fix ships with a content-asserting regression test, and a
final cross-cutting composition suite locks the multi-rewind + multi-shrink end-to-end behavior:

- **BUG-001:** `filterPipeline` with 2 users + `to_previous_prompt:true` → assert the LATEST user's
  text AND the post-user tail are GONE (content check), latest-user content absent, first user kept.
- **BUG-002:** `filterPipeline` checkpoint-crosses-latest → assert length UNCHANGED (no-op, no trim);
  `rewind.ts` checkpoint-crosses-latest → assert REFUSAL text + no marker persisted + no note sent.
- **BUG-003:** two `last_tool_call_group` rewinds WITHOUT `hideEntryIds` → assert both mistake spans
  absent AND both rewind confirmations present (roles + content).
- **BUG-004:** two `by_content_includes` shrinks same target → assert second replacement WINS.
- **BUG-005:** exactly-at-threshold result → nudge fires AND audit flags it (matched boundary).
