# PRP — P1.M2.T1.S3: Capture `hideEntryIds` at rewind creation (tools/rewind.ts resolvePreview)

## Goal

**Feature Goal:** At `mulligan_rewind` creation time, PIN the rewind's resolved target by recording the source `SessionEntry.id`s of every message it resolved to hide, storing them as `hideEntryIds: string[]` on the persisted `RewindMarker`. The pin is built from the SAME entry source the filter uses (`getBranch().slice().reverse()` projected via `sessionEntryToContextMessages`), so it is the exact inverse of the S2 `mapEntryIdsToMessageIndices` walk S4's filterPipeline will use to resolve it. This is the CAPTURE half of the BUG-002 fix; S4 (Planned) consumes the pin.

**Deliverable:** (a) MODIFY `resolvePreview` in src/tools/rewind.ts: switch source to `getBranch().slice().reverse()`, build a parallel `indexToEntryId` during the flat-map, compute `hideEntryIds` from the resolved `remove` set, and widen the return to `{ ledger, k, hideEntryIds }`; (b) MODIFY `rewindExecute` step 5 (destructure `hideEntryIds` + add it to the catch fallback) and step 7 (conditional-spread `hideEntryIds` onto the `RewindMarkerInput` ONLY when non-empty); (c) MIGRATE test/tools/rewind.test.ts fakes (`contextEntries` → `branch`, LEAF→ROOT order) and ADD the hideEntryIds-capture test + negatives. No other src file is touched.

**Success Definition:** `npx tsc --noEmit` passes (the conditional spread typechecks against `RewindMarkerInput.hideEntryIds?: string[]`); `npx vitest run test/tools/rewind.test.ts` is green (the 29 existing tests migrated + the new capture test + negatives); `npx vitest run` full suite green (baseline 635+, 0 regressions — the source switch touches ONLY tools/rewind.ts so filter.ts/transforms.ts/pipeline tests are unaffected); a marker persisted against a known-id fixture branch carries exactly the resolved toolGroup's entry ids in `data.hideEntryIds`; a marker with nothing to hide OMITS `hideEntryIds` (undefined, not `[]`).

## Why

- **BUG-002 root cause (critical):** `filterPipeline` re-resolves each rewind's target LIVE against the *current* (already-reduced) message list on every inference (spec D7). For `last_tool_call_group`, when a SECOND rewind marker exists, the FIRST rewind's 'last toolGroup' re-resolves to whatever is now last (often the second rewind's own group, or a newer non-rewound tool call) — NOT the span the agent originally shed. Net: **originally-hidden content reappears**, violating PRD success criterion #4. The fix = PIN each rewind's resolved target onto the marker at creation, then have the filter resolve against the pin (S4).
- **S3 is the capture side; S4 is the resolve side.** S4 (filterPipeline) will call `mapEntryIdsToMessageIndices(event.messages, branchEntries, hideEntryIds)` to turn the pinned entry ids back into CURRENT message indices. For that resolution to be CORRECT, the ids captured here MUST be the entry ids whose message positions (in the `getBranch().slice().reverse()` projection) equal the indices in `remove`. That is true BY CONSTRUCTION only if capture builds its message list + index→entryId map from the SAME source the filter uses. Hence the task's hard requirement: switch `resolvePreview` from `buildContextEntries()` to `getBranch().slice().reverse()`.
- **Why entry ids (not toolCallId):** design_decisions.md §BUG-002 'Why pin by ENTRY id' — entry ids work for ALL granularities (last_tool_call_group hides specific entries; last_turn/checkpoint generalize), the codebase's TODO comments already name `hideEntryIds`, and `resolveCheckpoint` already maps entries→messages via the same walk. Choosing entry ids now keeps the mechanism uniform.
- **Backward compat:** `hideEntryIds` is OPTIONAL on `RewindMarker`/`RewindMarkerLike` (S1 shipped it). Markers WITHOUT it (legacy, or capture-failed, or empty remove) fall back to live resolution in S4. The 635-test baseline stays green.

### The resolvePreview change (src/tools/rewind.ts)

Replace the current `resolvePreview` body (the `entries`/`messages`/`remove`/`ledger`/`return` block) with:

```ts
function resolvePreview(
  ctx: ExtensionContext,
  params: RewindArgs,
  toolCallId: string,
): { ledger: FileLedger; k: number; hideEntryIds: string[] } {
  const branchRaw = ctx.sessionManager.getBranch();
  const branchRootToLeaf: BranchEntry[] = Array.isArray(branchRaw) ? branchRaw.slice().reverse() : [];
  const messages: MessageLike[] = [];
  const indexToEntryId: string[] = [];
  for (const e of branchRootToLeaf) {
    const id = e && typeof e.id === "string" ? e.id : ""; 
    const yielded = sessionEntryToContextMessages(e); 
    for (const m of yielded) {
      messages.push(m as unknown as MessageLike);
      indexToEntryId.push(id); 
    }
  }
  let remove: number[];
  if (params.granularity === "last_tool_call_group") {
    const units = partitionIntoUnits(messages);
    remove = resolveLastToolCallGroup(units, messages, toolCallId) ?? [];
  } else if (params.granularity === "last_turn") {
    remove = resolveLastTurn(messages, { to_previous_prompt: params.to_previous_prompt }, toolCallId).remove;
  } else {
    remove = resolveCheckpoint(messages, branchRootToLeaf, params.checkpoint ?? "", toolCallId)?.remove ?? [];
  }
  const ledger = extractFileLedger(messages, remove);
  const hideEntryIds = remove
    .map((i) => indexToEntryId[i])
    .filter((id): id is string => typeof id === "string" && id.length > 0);
  return { ledger, k: remove.length, hideEntryIds };
}

```

## Anti-Patterns to Avoid

- ❌ Do NOT build indexToEntryId in a separate loop from messages — they MUST be pushed together (same loop, same order) so indexToEntryId[i] aligns with messages[i] exactly.
