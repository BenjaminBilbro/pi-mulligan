# PRP — BUG-005: Null-check refusal before leaveNote + test (P1.M3.T2.S1)

## Goal

**Feature Goal:** When `appendRewindMarker` cannot persist the rewind marker (returns `null` — either `pi.appendEntry` threw, or `ctx.sessionManager.getLeafId()` returned `null`), the `mulligan_rewind` tool MUST return a refusal text and MUST NOT leave a note, so the agent is never told a rewind succeeded when nothing will be hidden by the filter.

**Deliverable:** (a) ONE 3-line source insert in `src/tools/rewind.ts` `rewindExecute` step 7 (between `appendRewindMarker` and `leaveNote`) that reuses the existing `refusal()` helper; (b) UPDATE the single existing test that encodes the old null→fallback-note contract (`mulligan_rewind — leafId null fallback`); (c) ADD one new `describe` block with TWO cases (appendEntry throws; getLeafId null) asserting the new refusal contract, including a small `appendEntryCalls` counter on the `makePi` fake so "appendEntry attempted exactly once" is provable for the throw case.

**Success Definition:** `npx tsc --noEmit -p tsconfig.json` passes (strict mode, no type change); `npx vitest run test/tools/rewind.test.ts` is green (the updated test + the 2 new cases pass; the previously-loose `throwOnAppend` never-throws test still passes); `npm test` is fully green (691+ passed, 2 skipped, 0 newly broken). A failed persist now returns text starting with `Mulligan: refused —` and `pi.sendMessage` is NOT called.

## Why

- **Business value / user impact:** Today `appendRewindMarker` is fail-open and returns `null` on persist failure, but `rewindExecute` never checks — it proceeds to `leaveNote(...)` (injecting a STRAY `mulligan:note` into the LLM context for a rewind that did not happen) and returns the success text `Mulligan: rewound <granularity>. <K> messages will be hidden... Note left.`. The agent then believes it shed K messages that the filter will never hide (no marker exists). This is a silent correctness failure against spec success-criterion #4 ("hidden content is never silently lost" — here the inverse: the agent is told content was hidden when it was not) and the fail-open discipline's intent (errors must be observable, not disguised as success). See `plan/001_df2a6021905e/bugfix/001_8022a49f0aff/architecture/design_decisions.md` §BUG-005 and `TEST_RESULTS.md` BUG-005.
- **Root cause (verified by reading the source):** `src/tools/rewind.ts` lines 463–465: `const markerId = appendRewindMarker(pi, ctx, payload); leaveNote(pi, { content: rendered, rewindId: markerId ?? toolCallId });` — no null gate between them. `appendRewindMarker` (`src/markers.ts`) returns `string | null`: `null` when `pi.appendEntry(...)` throws (caught internally → `logError` → `return null`), AND `null` when `ctx.sessionManager.getLeafId()` returns `null` (the bare `return ctx.sessionManager.getLeafId()` is the last try-block statement).
- **Scope cohesion:** This is BUG-005, one of three independent minor fixes in milestone P1.M3 (BUG-004 branch scoping, BUG-005 silent persist failure, BUG-008 audit suggestion). It is surgical to `rewindExecute` step 7 — no new features, no API change, no filter/transform logic touched. It MUST NOT touch BUG-004 (`countRewindMarkers`/`checkpointExists`, already landed by P1.M3.T1.S1) or BUG-008 (`src/tools/audit.ts` Suggestion line, P1.M3.T3.S1).

## What

Insert a single null-check between `appendRewindMarker` and `leaveNote` in `rewindExecute` step 7. The check reuses the existing module-local `refusal(reason, granularity)` helper (rewind.ts ~line 122), which prefixes `"Mulligan: refused — "` and closes with `"."`, and returns `details: { granularity }` only (no `markerId`). The success path (`leaveNote + successText + details with markerId`) is UNCHANGED for the non-null case — the `markerId ?? toolCallId` in the `leaveNote` call becomes dead-but-harmless on the success path and is NOT removed.
