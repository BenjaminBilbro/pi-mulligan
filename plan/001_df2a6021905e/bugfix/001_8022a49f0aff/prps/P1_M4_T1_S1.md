## Why

- **Business value / user impact:** BUG-007 (TEST_RESULTS.md) calls out that the deterministic smoke suite passes 9/9 but leaves the F-shrink-preventive `bloatHit:true` headline assertion SOFT/"unprovable" — there is NO automated proof that `bloatReminderHandler` + `turnEndMetricHandler` actually record `bloatHit:true` in a real session. Nudge A (the bloated-result reminder) is one of Mulligan's two signature "free-ride" preventive mechanisms (spec/07 §1; spec/03 design principle #3 zero-extra-requests). Shipping without an integration proof means a regression that breaks the bloat path (e.g. someone re-introduces an over-broad tool-name skip, or breaks `pendingBloatHits` accumulation) would land silently. This task closes that gap with a deterministic, HARD-gated proof.
- **Root cause (verified by reading the source):** `src/nudges.ts` `bloatReminderHandler` line ~`if (typeof tn === "string" && tn.startsWith("mulligan_")) return;` — the skip is CORRECT (Mulligan must not annotate its own tools), but the smoke harness only ever registered `mulligan_*` big tools, so no registered tool could ever cross the threshold without being skipped. The fix is harness-side (register a non-`mulligan_*` tool), NOT a change to `bloatReminderHandler` (whose logic is already unit-tested in `test/turn_metric.test.ts` lines 93–254, including the exact "F-shrink-preventive: bloat handler then turnEndMetricHandler → metric bloatHit===true" case at line 212).
- **Scope cohesion:** This is P1.M4.T1.S1 — the FIRST of three independent M4 (BUG-007) subtasks. `dependencies: []` in tasks.json; it is "Independent of M1/M2 (purely a harness/tool-registration gap)". The default `bloatThresholdBytes=8192` applies with NO config customization (the repo's `.pi/settings.json` has no `mulligan` key → defaults), so it does NOT depend on M1's config wiring. It MUST NOT touch M2's pinning territory (`transforms.ts`/`markers.ts`/`filter.ts`/`rewind.ts`) or M4.T3's territory (the F-rewind-core/F-checkpoint hiding assertions in `run-smoke.mjs`). It is surgical to the F-shrink-preventive arm: smoke.ts (1 new tool registration + 1 recipe edit) + run-smoke.mjs (1 prompt-flow branch + 1 asserter upgrade) + scenarios.md (1 doc note).

### The new tool (VERBATIM shape — copy mulligan_smoke_big, change name + canary + remove the mulligan_ prefix)
```typescript
const BLOAT_CANARY = "MULLIGAN-SMOKE-BLOAT-CANARY"; 
pi.registerTool({
  name: "smoke_read_big", 
  label: "Smoke Read Big",
  description: "SMOKE TEST TOOL. Returns a large result (>8KB) to exercise the bloat reminder. Call when asked.",
  parameters: Type.Object({}),
  async execute() {
    const big = BLOAT_CANARY + " " + "x".repeat(10000);
    return { content: [{ type: "text" as const, text: big }] };
  },
});

```

### Why the model-prompt path (no model-free alternative — verified)
`bloatReminderHandler` fires on Pi's `tool_result` EVENT, which Pi dispatches ONLY when the agent loop executes a registered tool (the MODEL emitted a toolCall). There is NO extension-facing API to synthesize a `tool_result` event or to invoke a registered tool through the executor from a `/cmd` handler — `ExtensionAPI` exposes only `registerTool`/`on`/`appendEntry`/`sendMessage`/`setLabel`/`sendUserMessage` (no `executeTool`/`invokeTool`; verified against the dist types). Calling `bloatReminderHandler` directly from the smoke helper would mutate the SMOKE helper's own `config.ts`/`runtime.ts` instances (Pi's jiti loader gives each `-e` extension a SEPARATE module cache — documented in smoke.ts lines 31–37), NOT Mulligan's, so no real bloatHit would land in Mulligan's turn-metric. The deterministic command path (which the other scenarios use to call the REAL tool factories directly, e.g. `makeRewindTool(pi).execute(...)`) does NOT fire a `tool_result` event — it is a plain function call — so it cannot trigger `bloatReminderHandler` either. **Therefore the sanctioned path is the model-prompt approach** (explicitly allowed by the work item: "via a model prompt or by invoking the tool through pi"). The prompt `"Call the smoke_read_big tool, then reply with exactly: OK"` reliably triggers the call with the default model glm-5.2 (spike-proven — see Context). This makes F-shrink-preventive model-dependent for the observing turn, exactly like F-rewind-core's authoritative canary-drop proof (documented in scenarios.md).

### SPIKE PROOF (run 2026-08-11 against this repo + glm-5.2)
A throwaway extension registering `smoke_read_big` (returns `"SMOKE-BLOAT-CANARY " + "x".repeat(10000)`) was loaded as `-e ./src/index.ts -e /tmp/spike.ts` and driven with `-p "Call the smoke_read_big tool, then reply with exactly: DONE"`. Session-JSONL readback:
- `smoke_read_big` toolResult present (count=1) → **the model called the non-mulligan tool**.
- turn-metric #1: `"bloatHit":true`, `"bloatHits":[{"toolName":"smoke_read_big","approxTokens":2505}]`.
- `[mulligan]` reminder block appended to the tool_result (count=1) → `bloatReminderHandler` FIRED on the real event.
- turn-metric #2 (next turn): `bloatHit:false` (no bloat) — confirms the metric is correctly per-turn.

This empirically validates the entire chain: tool registration → model call → real `tool_result` event → `bloatReminderHandler` appends reminder + pushes `pendingBloatHits` → `turnEndMetricHandler` snapshots at `turn_end` → `appendTurnMetric` persists `bloatHit:true` to the session JSONL.
