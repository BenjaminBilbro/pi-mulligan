# PRP for P1_M1_T2_S1

## Objective

Wire the default-exported factory in src/index.ts and its existing `session_start` handler to call `setConfig(loadMulliganSettings(...))`, so the already-shipped pure disk-reader (P1.M1.T1.S1: src/settingsLoader.ts) actually feeds real settings.json into the already-correct-but-starved `config.ts:setConfig`/`validateConfig`. Concretely: (a) at the TOP of the factory body, BEFORE setLogFile, add `try { setConfig(loadMulliganSettings({})); } catch { /* never break load */ }` (global-only best-effort — the factory receives only `pi: ExtensionAPI`, NO ctx, so cwd is unavailable); (b) inside the existing `pi.on("session_start", (event, ctx) => {...})` handler, BEFORE resetRuntime, add `try { setConfig(loadMulliganSettings({ cwd: ctx.cwd, isTrusted: ctx.isProjectTrusted() })); } catch { /* never break session start */ }`, KEEP the existing `resetRuntime(ctx.sessionManager.getSessionId())` call, THEN re-call `setLogFile(getConfig().log.file)` so a `/reload` that changed `mulligan.log.file` takes effect (log.file was read once at factory time). Re-read on EVERY session_start reason (startup|reload|new|resume|fork) — cheapest correct, and `session_start` already fires on `/reload`, so this SINGLE wiring fixes BOTH BUG-001 (config never read) and BUG-006 (not re-read on /reload). The factory STAYS SYNCHRONOUS (no async/await per D8). Minimal update to test/index.test.ts so the existing baseline stays GREEN (one test must reorder its setConfig relative to factory invocation). config.ts and settingsLoader.ts are NOT modified (scope boundary).

## Context

## Goal

**Feature Goal**: Make `src/index.ts` honor `mulligan` config from Pi's `settings.json` files by wiring the already-shipped `loadMulliganSettings` (P1.M1.T1.S1) into the factory load path AND the `session_start` handler, feeding real merged settings into the already-correct `config.ts:setConfig`/`validateConfig`. This closes BUG-001 (critical: config surface entirely inert — `getConfig()` always returned `DEFAULT_CONFIG` because the factory never called `setConfig`) and BUG-006 (minor: config not re-read on `/reload`) in a single wiring change.

**Deliverable**: A modified `src/index.ts` whose (a) factory body opens with a try/catch-wrapped `setConfig(loadMulliganSettings({}))` before the existing `setLogFile(getConfig().log.file)`; (b) `session_start` handler calls `setConfig(loadMulliganSettings({ cwd: ctx.cwd, isTrusted: ctx.isProjectTrusted() }))` before `resetRuntime(...)`, keeps `resetRuntime(...)`, and re-calls `setLogFile(getConfig().log.file)` after. Imports: `setConfig` added to the `./config.js` import; new `import { loadMulliganSettings } from "./settingsLoader.js";`. Plus a minimal `test/index.test.ts` update (reorder one test's `setConfig` to AFTER `factory(pi)` invocation) so the 652-test baseline stays GREEN. The factory remains `export default function (pi: ExtensionAPI): void` — synchronous.

**Success Definition**: (1) `setConfig(loadMulliganSettings({}))` runs at the top of the factory (global-only, best-effort, never throws); (2) the `session_start` handler re-reads+sets config with `ctx.cwd`+`ctx.isProjectTrusted()` on EVERY reason, before resetRuntime, then re-applies `setLogFile`; (3) the existing `resetRuntime(ctx.sessionManager.getSessionId())` call is preserved unchanged; (4) `npm test` is GREEN (baseline 652 passed | 2 skipped + the updated index test); (5) `npx tsc --noEmit -p tsconfig.json` exits 0; (6) `src/config.ts` and `src/settingsLoader.ts` are NOT modified (scope boundary); (7) the factory is NOT async (D8).

## Why

- **BUG-001 (critical):** today the factory (`src/index.ts`) never calls `setConfig`, so `getConfig()` always returns `validateConfig(undefined)` = `DEFAULT_CONFIG`. Every documented knob (enabled, thresholds, maxDepth, log.file, …) is inert, and README §3's "`enabled: false` → all four tools refuse" is a false claim. The fix is NOT in config.ts (it is already correct — verified: `validateConfig(undefined)` returns DEFAULT_CONFIG because `isRecord(undefined)===false`); it is purely that config.ts was never fed real input. Pi's `ExtensionAPI` exposes NO settings accessor (architecture/external_deps.md §1, confirmed by grep of `types.d.ts`), so the ONLY way to honor spec/09 §1 is to read the JSON files from disk — which P1.M1.T1.S1 already shipped (`src/settingsLoader.ts`). This task is the WIRING that connects them.
- **BUG-006 (minor):** README §3 promises config is "re-read on `/reload`". `session_start` already fires on `/reload` (its `reason` union is `"startup"|"reload"|"new"|"resume"|"fork"`), so calling `setConfig(loadMulliganSettings(...))` inside the `session_start` handler on EVERY reason closes BUG-006 for free — no reason-branching needed.
- **Why factory + session_start (two read points):** the factory signature `export default function (pi: ExtensionAPI): void` receives NO ctx, so project-local config (which needs `ctx.cwd`) can ONLY be read inside an event handler. Reading GLOBAL config (needs only `os.homedir()`, which `loadMulliganSettings` computes internally) at factory time means config is populated even BEFORE the first `session_start` fires — defense for any early `getConfig()` call (e.g. tool registration, the `setLogFile(getConfig().log.file)` line immediately below). The `session_start` read then adds the project-local overlay (cwd + trust) and keeps config fresh across reload.
- **Why re-call setLogFile after setConfig in session_start:** `mulligan.log.file` is read once at factory time. On `/reload`, the user may have edited `.pi/settings.json` to change it; re-calling `setLogFile(getConfig().log.file)` after the `session_start` setConfig makes the new log path take effect. (`log.ts:setLogFile` is idempotent and cheap — just reassigns the module-level destination.)

1. **Factory imports** — change `import { getConfig } from "./config.js";` to `import { getConfig, setConfig } from "./config.js";` and ADD `import { loadMulliganSettings } from "./settingsLoader.js";`.
2. **Factory body, item 0 (NEW, at the very TOP, before the existing `setLogFile` line):**
   ```ts
   try { setConfig(loadMulliganSettings({})); } catch {  }
   
```
   The existing `setLogFile(getConfig().log.file);` line stays immediately after it (now reading the just-set config instead of DEFAULT_CONFIG). All other factory steps (register 4 tools, attach context/tool_result/turn_end/session_start/session_shutdown handlers) are UNCHANGED.
3. **`session_start` handler** — currently `pi.on("session_start", (event, ctx) => { resetRuntime(ctx.sessionManager.getSessionId()); });`. Replace its body with:
   ```ts
   pi.on("session_start", (event, ctx) => {
     try { setConfig(loadMulliganSettings({ cwd: ctx.cwd, isTrusted: ctx.isProjectTrusted() })); } catch {  }
     resetRuntime(ctx.sessionManager.getSessionId());
     setLogFile(getConfig().log.file);
   });
   
```
   `event` remains unused in the body (it was unused before too — do NOT branch on `event.reason`; re-read unconditionally). `resetRuntime(...)` and `clearAll()` (in `session_shutdown`) are preserved exactly.
4. **NO async/await (D8).** `setConfig`, `loadMulliganSettings`, `setLogFile`, `getConfig` are ALL synchronous. The factory signature stays `export default function (pi: ExtensionAPI): void`. Adding `async` would change the return type to `Promise<void>` and violate spec D8.
5. **Never-break discipline.** Both new `setConfig(loadMulliganSettings(...))` calls are wrapped in `try { ... } catch { /* swallow */ }`. (`setConfig` and `loadMulliganSettings` each already never throw — both have internal try/catch — so the outer try/catch is belt-and-suspenders defense-in-depth, mirroring `config.ts:warnConfig`, `log.ts:writeStderrFallback`, and `settingsLoader.ts:warnUnreadable`.) A failure MUST NOT prevent tool registration (factory) or runtime reset (session_start).
6. **test/index.test.ts update (REQUIRED to keep baseline GREEN).** The existing test `"should pass-through context when enabled=false"` BREAKS after wiring: it calls `setConfig({ enabled: false })` THEN `factory(pi)`, but the factory now overwrites that by reading the REAL `~/.pi/agent/settings.json` (confirmed: NO `mulligan` key → returns `undefined` → `setConfig(undefined)` → DEFAULT_CONFIG → `enabled:true`), so `contextHandler` no longer returns `undefined`. FIX: reorder that ONE test so `factory(pi)` is invoked FIRST (settling config to DEFAULT_CONFIG from the real global file — deterministic on this machine) and `setConfig({ enabled: false })` is called AFTER (so disabled config is the last thing set before the assertion). Do NOT mock `node:os`/`node:fs` for this — the reorder is sufficient and hermetic. Leave the `setConfig({ enabled: true })` reset at the end of that test intact. The other 5 tests in index.test.ts do NOT break (verified by reading each body): "factory does not throw", "4 tools", "5 event handlers", and "zero-config load" all pass with DEFAULT_CONFIG; "refuse all 4 tools when enabled=false" imports the tool modules directly (NOT `index.js`), so the factory is never invoked and its `setConfig({enabled:false})` stands.
