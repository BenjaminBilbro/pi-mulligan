It exposes a pure, fail-safe `validateConfig(raw: unknown): MulliganConfig` (the unit-testable engine), a session-cached `getConfig(): MulliganConfig` (lazy, defensive-copy), a `setConfig(raw)` seam (the Pi-settings + /reload injection point), the `MulliganConfig` interface, and the `DEFAULT_CONFIG` constant. ## Why

- This is the dependency root for the entire M1 milestone and most of M2–M4. CONTRACT §4 lists the consumers: `getConfig()`/`validateConfig()` are consumed by filter.ts (P1.M3.T2), EVERY tool (P1.M4.T1–T4), and nudges.ts (P1.M3.T3). log.ts (P1.M1.T3, the next task) reads `config.log.file`. Without config.ts, nothing downstream compiles or behaves.
- Establishes the **fail-open / never-throw** contract that is load-bearing for the whole extension (spec/08 E13, E14): a single malformed `settings.json` field must NOT break the agent loop. This task makes that guarantee concrete at the config layer.
- Resolves the one genuinely open question (CONTRACT §2): **there is NO Pi settings accessor on `ExtensionAPI`/`ExtensionContext` in Pi 0.84.x** (verified: the only `getConfig*` symbols in `node_modules/@earendil-works/pi-coding-agent/dist/**/*.d.ts` are unrelated provider-config helpers). Therefore the architecture is: `getConfig()` lazily caches validated `DEFAULT_CONFIG`; `setConfig(raw)` is the seam that index.ts (a later task) calls at factory time and on /reload, handing in the merged Pi `settings.mulligan` object when one exists (v1 ships zero-config: `setConfig(undefined)` → defaults). config.ts stays Pi-free and unit-testable.

- [ ] Unknown keys ignored (forward-compat), incl. a reserved `shrink.autoOnBloat` (not v1) — no warn for unknown keys.
- [ ] `validateConfig` NEVER throws — including on a circular reference, a Proxy with a throwing `get` trap, a primitive arg, or an array arg (all → defaults). ABSENT fields are NOT warned (only present-but-invalid values warn).
- [ ] `validateConfig` does NOT mutate `DEFAULT_CONFIG` (operate on a `structuredClone`).
- [ ] `getConfig()` lazily validates+caches `DEFAULT_CONFIG` on first call, returns a fresh `structuredClone` on EVERY call (callers cannot poison the cache by mutating the returned object).
- [ ] `setConfig(raw)` validates `raw` and replaces the cache; on any error resets the cache to validated defaults; never throws.
- [ ] Scope honored: NO log.ts import; NO Pi import; NO wiring into index.ts (that is a later task); NO `autoOnBloat` field; NO per-tool threshold map.

### Implementation Patterns & Key Details
```ts
export function validateConfig(raw: unknown): MulliganConfig {
  try {
    const cfg = structuredClone(DEFAULT_CONFIG);   
    if (!isRecord(raw)) return cfg;                
    let v: unknown;
    v = safeGet(raw, "enabled"); if (v !== undefined) cfg.enabled = coerceBoolean(v, cfg.enabled);
    return cfg;
  } catch {
    return structuredClone(DEFAULT_CONFIG);        
  }
}
function coerceNumber(field: string, value: unknown, fallback: number, mustBePositive: boolean): number {
  if (typeof value === "number" && Number.isFinite(value) && (mustBePositive ? value > 0 : value >= 0)) return value;
  warnConfig(field, value);                         
  return fallback;
}
function safeGet(obj: object, key: string): unknown {
  try { return (obj as Record<string, unknown>)[key]; }
  catch { return undefined; }
}
```
